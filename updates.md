# updates.md — change log for RenovaTrack

Every change to this project gets an entry here. Newest at the **bottom**.

This is the history. `about.md` is the reference for how things currently work.

## How to add an entry

Copy this template. Plain English — write it so it still makes sense in a year.

```markdown
### YYYY-MM-DD — Short title of what changed

**What changed (in plain English):**
One or two sentences. What is different now that wasn't before.

**Why:**
What problem this solved, or what was wrong.

**Where the information came from:**
Spreadsheet + sheet name, table, screen, or "user request".

**Files used (read, not changed):**
- `path/to/file`

**Files changed:**
- `path/to/file` — what changed in it

**Database:**
Migration file, whether it has been run in the Supabase SQL editor, and any
figures that moved. Write "none" if nothing touched the database.

**Result / numbers after:**
The figures that changed, before → after.
```

Rules:

- One entry per change, even small ones.
- Always name the **files used** and the **files changed** — that is how you
  retrace a change later.
- Always say whether a migration **has actually been run**, not just written.
- If a headline figure moved, show it as `before → after`.

# History

### 2026-07-20 — Everything disappeared, and getting it back

**What changed (in plain English):**
The app suddenly showed no data at all. The cause was found and all the data
was rebuilt from the original spreadsheets.

**Why:**
The `admin@pk.com` login had been deleted and recreated in Supabase. Every
table is wired so that deleting a user also deletes all their rows
(`on delete cascade`), so recreating the account did **not** bring anything
back — the new account was a different user as far as the database was
concerned, even with the same email address.

Confirmed by counting rows directly in the SQL editor: 0 projects, 0 expenses,
0 weeks. The 13 trade lookups that *were* there turned out to be a red herring
— a trigger creates those automatically for every brand-new account, so they
were new, not survivors.

**Where the information came from:**
The two spreadsheets in the project folder, which are the master copy:

- `46_Glenferrie_Rd_Renovation_Spend_Tracker_Blank_Template.xlsx` — the
  week-by-week diary
- `Renovation_Cost_Tracker-1.xlsx` — the trades and materials ledger

**Files used (read, not changed):**
- both spreadsheets above

**Files changed:**
- `scripts/build_import_sql.py` — **new**. Reads both spreadsheets and writes
  out the SQL needed to rebuild everything
- `supabase/migrations/0005_reimport_data.sql` — **new**, generated by that
  script
- `supabase/migrations/0004_reassign_orphaned_data.sql` — **deleted**. It had
  been written on the wrong assumption (that the rows still existed under an
  old user ID) and was never run

**Database:**
`0005_reimport_data.sql` — **run** in the Supabase SQL editor. Restored:

- 40 diary rows (weeks 1–15)
- 96 ledger rows
- 16 trade lookups

All under the new user ID `5d3fc9ff-92a3-4923-a18b-7eb5eade3105`. The ledger
total came to £98,932.12, matching the Dashboard sheet in the spreadsheet — a
good sign the import was faithful.

**Result / numbers after:**
Data visible again. 20 of the paid dates in the spreadsheet were written as
free text (`Friday 27/2`) and couldn't be stored in a proper date column, so
they were parked in each row's notes for the time being.

**Left as-is on purpose:** the `on delete cascade` wiring is unchanged. If the
login is deleted again, the same thing will happen again.

### 2026-07-22 — Dashboard said 144%, the project page said 44%

**What changed (in plain English):**
The project card on the Dashboard was showing £142,618.29 spent and "144% of
budget used", while opening the same project showed £43,686.17 and 44%. The
Dashboard was wrong. It now shows the same 44%.

**Why:**
Expense rows come in two kinds. **Diary** rows are the week-by-week plan (from
the first spreadsheet). **Ledger** rows are imported reference rows for the
Trades and Materials tabs (from the second spreadsheet). The two overlap — they
partly record the same spending from different angles — so they must never be
added together.

The project page knew this and only counted diary rows. The Dashboard didn't,
so it counted both:

```
£43,686.17  (diary)
+ £98,932.12  (ledger)
= £142,618.29  ← what the card was showing
```

Worse, the budget it was measured against (£98,932.12) *is* the ledger total,
so the card was effectively comparing the ledger against itself and then adding
the diary on top. It was always going to read over 100%.

**Where the information came from:**
Comparing the two screens and confirming the arithmetic matched exactly.

**Files used (read, not changed):**
- `components/project/ProjectDetail.tsx` — the correct version of the filter
- `lib/summary.ts`, `lib/calculations.ts` — to confirm both screens otherwise
  calculate spend identically

**Files changed:**
- `app/(app)/dashboard/page.tsx` — added a filter so ledger rows are left out
  of the card total, matching what the project page already did

**Database:**
None. This was a display bug only — no data was wrong.

**Result / numbers after:**

| | Before | After |
|---|---|---|
| Spent (card) | £142,618.29 | £43,686.17 |
| % of budget | 144% | 44% |

Both screens now measure the same thing the same way.

### 2026-07-22 — Marking the paid weeks as Paid

**What changed (in plain English):**
20 expense rows (weeks 1–7) were sitting as "Planned" even though the
spreadsheet shows them as paid. They are now marked **Paid**, with the amount
paid and the real payment date filled in. "Paid to Date" went from £0.00 to
£13,273.40.

**Why:**
The Overview tab showed "Paid to Date £0.00", which was obviously wrong.

The reason turned out to be a quirk of the spreadsheet. Its **Status** column
says "Planned" on all 40 rows — it was never updated as work got paid for. What
actually records a payment is the **Paid Date** column, which is filled in on
20 rows and blank on the other 20. The original import copied the Status column
literally, so everything came in as Planned.

There was a second wrinkle. The paid dates are hand-typed as things like
`Friday 27/2` — a weekday, a day and a month, but **no year**. The year was
worked out from the weekday: across all seven distinct dates, 2026 is the only
year where every one of them actually falls on the Friday it claims. So the
dates could be stored properly instead of being left as text.

**Where the information came from:**
`46_Glenferrie_Rd_Renovation_Spend_Tracker_Blank_Template.xlsx`, the
**Week-by-Week Plan** sheet — specifically the `Paid Date` column (column I).

Rows with a paid date: weeks 1–7 (20 rows, £13,273.40).
Rows without: weeks 8–15 (20 rows, £29,138.41).

**Files used (read, not changed):**
- `46_Glenferrie_Rd_Renovation_Spend_Tracker_Blank_Template.xlsx` (Week-by-Week
  Plan sheet)
- `lib/summary.ts`, `lib/calculations.ts` — to work out the knock-on effects
- `supabase/migrations/0005_reimport_data.sql` — to match rows against what is
  already in the database

**Files changed:**
- `scripts/build_import_sql.py` — added `resolve_written_date()`, which turns
  `Friday 27/2` into a real date by checking which year puts it on a Friday. A
  row with a resolved paid date is now imported as Paid, with the paid amount
  filled in. Also removed the now-unnecessary "paid date kept in notes" workaround
- `supabase/migrations/0005_reimport_data.sql` — regenerated by that script
- `scripts/gen_mark_paid_sql.py` — **new**. Writes the patch below
- `supabase/migrations/0006_mark_paid_entries.sql` — **new**, generated

**Database:**
`0006_mark_paid_entries.sql` — **run** in the Supabase SQL editor. Verified
result: `paid_rows 20 | planned_rows 20 | paid_total 13273.40 | stale_notes 0`.

Safety features of that migration:

- It matches rows on week number + description + quoted amount, which is unique
  across all 40 rows
- It **aborts and rolls back** unless exactly 20 rows are updated, so a
  mismatch fails loudly rather than half-applying
- It can be re-run safely — running it twice changes nothing

**Result / numbers after:**

| | Before | After |
|---|---|---|
| Paid to Date | £0.00 | £13,273.40 |
| Remaining to Pay | £43,686.17 | £30,412.77 |
| Rows marked Paid | 0 | 20 |
| Actual Total | £43,686.17 | unchanged |
| Budget used | 44% | unchanged |

**Worth knowing:** "Paid to Date" adds up amounts *excluding* VAT, while
"Actual Total" *includes* VAT. So "Remaining to Pay" still carries the VAT on
rows that have already been paid. That quirk was already in the app and was not
introduced here — see `about.md` §6.2.

### 2026-08-05 — Catching price rises and typos as you enter them, and a proper phone layout

**What changed (in plain English):**
Four things, all aimed at making it quicker and safer to log a cost on your
phone while standing on site, instead of going home to a spreadsheet.

1. **You now get told when something costs more than last time, before you
   save.** Type a material's name and the form shows what you paid last time.
   Type the new unit price and it immediately says, in red, how much more it is
   — e.g. *"Last time Bricks was £5.00/unit on 2026-03-12 — now £10.00/unit
   ▲ +100.0%"*. The Overview tab also grew an amber banner listing every item
   whose latest price went up, so a rise is visible without opening the Price
   Tracker tab at all.

2. **Less typing.** Description and Supplier now suggest what you have typed
   before, as you type. A new **Repeat** button on every expense copies a past
   entry into a fresh one — same item, same supplier, same quantity — leaving
   only the price to change. Optional fields (date paid, payment method, room,
   invoice reference, notes, receipt) are folded away behind a toggle, so a
   quick entry is now about five fields long.

3. **The form warns about likely mistakes.** Three new amber notices, none of
   which stop you saving: the same item already logged in the same week for the
   same amount; a Paid figure larger than the Actual figure; and, for materials,
   Qty × Unit Cost not matching the Actual amount (with a one-click fix).

4. **The app works properly on a phone.** The bottom tab bar is gone, replaced
   by a hamburger menu that slides in from the left — the pattern most phone
   apps use. Every wide table (Expenses, Trades, Materials, Price Tracker,
   Week-by-Week) now shows as a stack of readable cards on a phone and stays a
   table on a computer. Number fields bring up the number keypad, the receipt
   picker offers the camera, and the Save/Cancel buttons stick to the bottom of
   the form so you never have to scroll to find them.

Also removed, as agreed: the **Completion %** column on the Overview tab's
Week-by-Week table. It was the only figure in the app that had to be typed in by
hand, and nothing else used it — it fed no total, no chart and no export.

**Why:**
The original problem this app was built for: paying £100 for 20 bricks and then
£200 for the same 20 bricks later, without noticing. The Price Tracker tab
already detected that, but only if you remembered to go and look. Now it comes
to you at the moment you are entering the number, which is the moment it is
useful. The other changes attack the same friction from the other side — the
less typing an entry takes, the more likely it gets logged at all.

**Where the information came from:**
User request. No spreadsheet or database figures were consulted or changed.

### 2026-08-06 — Weeks 16–23 added, and the double-VAT bug that made the app disagree with the spreadsheet

**What changed (in plain English):**
The app now holds the whole job to date — **weeks 1 to 23 instead of weeks 1 to
15**, 111 cost lines instead of 40. Everything from week 16 onwards (the roof,
the windows, the kitchen, the stairs, the bathrooms, the plastering, the
flooring, the June Lawsons invoices, and the rest) is now in the Expenses tab,
the weekly chart and every Overview figure.

While loading it, a real bug came to light in how the *existing* 15 weeks had
been imported, and it is now fixed. **The app had been adding VAT twice.** The
spreadsheet's "Total incl. VAT" figure was being stored in the app's "Actual"
box, and the app then added VAT on top of it when working out totals. That is
why the app said the first 15 weeks came to **£43,686.17** when the spreadsheet
said **£42,411.81** — the £1,274.36 difference was VAT counted a second time.
Amounts are now stored the way the app expects (before VAT), so every figure on
every screen equals the spreadsheet to the penny.

Three smaller consequences of that fix, all deliberate:

- **"Paid to Date" and "Remaining to Pay" now match the spreadsheet's own
  Payment Status box exactly** (£13,273.40 paid, £138,371.38 still committed).
  The app now records what was actually handed over, which includes VAT.
- **"Variance vs Quote" now reads £0.00** instead of a made-up £1,274.36
  overrun. The Week-by-Week Plan has no separate quote column — the plan *is*
  the quote — so there is nothing to be over or under by.
- **"Budget used" now reads 153% and shows red.** That is not an error. The
  Target Budget (£98,932.12) still comes from the *other* spreadsheet,
  `Renovation_Cost_Tracker-1.xlsx`, and spending has now passed it. The updated
  spreadsheet's own "Target Budget" cell is blank, so there was nothing better
  to replace it with. Say the word and it can be set to any figure.

**Why:**
The user supplied an updated tracker covering eight more weeks and asked that
the app and the spreadsheet agree. Loading the new weeks was straightforward;
making them *agree* meant fixing how money had been mapped into the database in
the first place, because weeks 16–23 contain far more VAT-bearing rows than
weeks 1–15 did, and the double-counting would have grown from £1,274 to
£9,958.

**Where the information came from:**
`46_Glenferrie_Rd_Renovation_Spend_Tracker_Updated.xlsx` — the "Week-by-Week
Plan" sheet for the 111 cost lines, the "Summary" sheet for the week totals and
the Paid/Committed figures used to check the import, and the "Lookups" sheet for
the 16 trade rates. The 96 reference rows behind the Trades and Materials tabs
still come from `Renovation_Cost_Tracker-1.xlsx` and are untouched.

Weeks 1–15 were compared line by line against the previous spreadsheet first:
the same 40 rows for the same money. The only differences are that the updated
file writes VAT as text ("0%") rather than a number, and — helpfully — moves
materials costs into the Materials column where the older file had put them in
the Labour column.

**Files used (read, not changed):**
- `about.md`, `updates.md`
- `46_Glenferrie_Rd_Renovation_Spend_Tracker_Blank_Template.xlsx` — the old
  weeks 1–15 file, used only to confirm nothing in those weeks changed
- `Renovation_Cost_Tracker-1.xlsx`
- `lib/summary.ts`, `components/project/OverviewTab.tsx`,
  `components/project/TradesTab.tsx`, `components/project/MaterialsTab.tsx`

**Files changed:**
- `scripts/build_import_sql.py` — reads the updated spreadsheet; maps money
  correctly (Actual = labour + materials, before VAT; Quoted and Paid = the
  sheet's incl-VAT total); refuses to write anything if a row's own

### 2026-08-14 — Written the build instructions for the next three phases

**What changed (in plain English):**
A new document, `phase_prompts.md`, containing three ready-to-use briefs — one
each for Phase 0, Phase 1 and Phase 3 of the "Route C" restructure described in
`renovatrack_evolution_summary.md`. Nothing in the app, the database or the
data changed. This is planning paperwork only.

Phase 0 is the new set of tables (suppliers, materials, invoices with several
lines on them, and payments as their own records) plus a one-off copy of the
existing expense rows into that new shape, with every current screen left
alone. Phase 1 is the pair of read-only screens that pays for it: pick a
supplier and see everything ever bought from them with what is still owed, or
pick a material and see what it has cost over time. Phase 3 is bulk-importing a
spreadsheet through a review screen where nothing saves until it is accepted
row by row. Phases 2, 4 and 5 are left for later.

**Why:**
The evolution summary describes what to build but not how to build it inside
*this* project, which has several rules that are easy to trip over — VAT is
applied on reading, not stored; the "diary" and "ledger" rows overlap and must
never be added together; new tables are invisible without a security policy;
migrations are pasted in by hand. Each brief carries those rules with it, so
they do not have to be rediscovered three times.

Three things worth flagging that the briefs now handle explicitly:

- **Migration `0007` still has not been run.** Until it is, the database holds
  40 rows for weeks 1–15, not the 111 rows for weeks 1–23 the spreadsheet now
  describes. Phase 0 copies whatever is actually in the database, and running
  `0007` afterwards would delete the rows it was built from. The document says
  to settle this first.
- **The diary/ledger split has to survive the move.** The new invoice table
  gets its own column to carry it, kept separate from the column recording

### 2026-08-17 — Invoice ingestion, Phase 4: the three API routes

**What changed (in plain English):**
Four new Route Handlers so a photographed or PDF'd invoice can travel from the
browser into `purchases`, with no UI yet:

- `POST /api/invoices/upload-url` — the browser asks for somewhere to put a
  file; gets back a Supabase signed *upload* URL and a new `invoice_uploads`
  row (`status: 'pending'`). The file itself is never sent to this route —
  the browser PUTs it straight to Storage with the signed URL, because
  Vercel caps a serverless request body at 4.5MB and a phone photo is
  routinely bigger than that.
- `POST /api/invoices/[id]/extract` — downloads the file server-side, calls
  the already-written extractor and resolver (`lib/invoice/extract.ts`,
  `resolve.ts`), and moves the row to `'extracted'` with the model's raw
  answer, the reconciliation warnings, and the supplier/item match
  candidates. Every exit path — success, a bad extraction, a storage
  failure, an unhandled throw — lands on a terminal status. Calling it again
  on a `'failed'` row retries cleanly.
- `POST /api/invoices/[id]/commit` — takes the reviewed (and possibly
  hand-edited) payload and writes it through `createPurchase` in
  `lib/purchaseWrite.ts`, the same function the manual multi-line form
  already uses, so there is still exactly one place that turns a form body
  into `purchases` + `purchase_lines` + `payments`. On top of that it always
  records the invoice's raw supplier string as a `supplier_aliases` row, and
  if a brand-new supplier was accepted, flags it `is_unverified` with
  `created_from_upload_id` set — but only when the name genuinely didn't
  already exist, checked before the write, because there is no way to tell
  "just created" from "already existed" apart afterwards.
- `GET /api/invoices/[id]` — the upload row plus a 5-minute signed *read* URL
  for the original file, for a future review screen to show the source
  document. Same pattern as the existing receipt route's GET.

**Why:**
This is Session 2 (Phase 4) of `invoice_ingestion_phase_prompts.md`. Phases
1–3 (schema, extractor, resolver) were audited and fixed in the previous
session; nothing could reach them from the app until these routes existed.
Phase 5 (the upload UI and review screen) is next.

**Where the information came from:**
`invoice-ingestion-prompt.md` (Phase 4 and Constraints) and
`invoice_ingestion_phase_prompts.md` (Session 2's brief) were the spec.
